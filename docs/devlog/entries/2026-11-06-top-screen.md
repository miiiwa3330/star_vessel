# タイトル画面と準備画面

世界がある程度できたので、サービスの画面づくりを始めた。最初は Top から。仕様は [`../../product/top-screen.md`](../../product/top-screen.md)。

## 決めたこと（オーナーの選択）

最初に「Top は何をする画面か」が docs のどこにも決まっていなかったので、選択肢と推奨を示して聞いた。

- **役割**：オーナーは「独立した紹介ページ」を選んだ。私の推奨は「世界を背景にした入口」だったが、選ばれなかった。同時に「景色が主役、文字は最小限」も選ばれ、2 つがぶつかったので聞き直したところ、**「タイトル画面と準備画面を分けたい」**となった。タイトル画面が景色、準備画面が中身（宇宙船・アカウント）
- **載せるもの**：出発ボタン・宇宙船を選ぶ・アカウントの登録とログイン・いま遊んでいる人数（4 つとも）
- **登録の方式**：「Google ログインか、パスキーか、一意のユーザー名とパスワード」。どれか 1 つを選んだのではなく候補が 3 つ挙がったので、**手元で確かめられ、外のサービスの設定も個人情報（メール）も要らないユーザー名＋パスワードから作った**。残りは「決まっていないこと」に推奨（パスキーを先に）つきで置いた

## つくり方の判断

- **世界を `/play` に移し、`/` をタイトル画面にした**。世界は起動時に約 78 MB のデータを読むので、タイトル画面で読ませたくない。どの URL も同じ `index.html` を返す（Cloudflare の SPA 設定・開発サーバーの既定）ので、`src/entry.ts` が `location.pathname` で動的 import を分ける。ルーターのライブラリは足していない（画面が 3 つのため）。**これまでの確かめ用の URL（`/?asteroids=bright` など）は `/play?...` に変わった**ので、AGENTS.md・README を直した
- **タイトル画面ではアカウントを作らない**。見るだけの人の匿名アカウントが増えるのを避けるため。準備画面を開いたときに作る（船の色がアカウントで決まるので、本当の色で見せたい。どのみち出発すれば作る）
- **背景は 2D の星空と CSS の地球の縁**。世界の描画（three.js）を使うと、タイトル画面が重くなる。本番ビルドを `vite preview` で配って測ると、タイトル画面は約 72 KB（gzip）。準備画面を開くと、船のプレビューに three.js などが約 239 KB 追加される。準備画面（Better Auth のクライアントを含む）も、開くときに読むようにした（最初はタイトル画面と一緒に読んでいた）
- **ユーザー名だけで登録する工夫**：Better Auth はアカウントごとにメールを必須とする。そこで、ユーザー名の小文字から作った仮のアドレス（`...@users.star-vessel.invalid`。`.invalid` は実在しないと決められている）を内部だけで使う。画面には出さない。副作用として、**パスワードを忘れても戻す方法が無い**（登録の画面に書いた）。将来メールを集めるときは、仮のアドレスを置き換える作業が要る
- **匿名の記録の引き継ぎ**：[`server.md`](../../tech/server.md) に前から「登録を作るときに必ず足す」と書いてあった処理。ワープホールは、合計が 3 個を超えても消さない（全員で共有しているので、持ち主のいない 3 個目以降を作らない。置けなくなるだけ）。宇宙船は登録した側を優先、訪れた天体は合わせて早い日時。SQL の組み立てを純粋な関数にして、本物のテーブル（`migrations/`）を `node:sqlite` に作ってテストした
- **人数はタイマー無しで数える**：宇宙の部屋は alarm を使わない決まり（alarm は 1 回ごとにリクエストとして数えられるため）。そこで、部屋が D1 の表に「部屋・数・時刻」を、つながったとき・切れたとき・前に書いてから 1 分たったあとのメッセージのときに書く。数える側は 150 秒より新しい行だけ足す。部屋が知らせずに消えても、行は自然に数えなくなる。別案の「全部屋を束ねる 1 つの Durable Object に足し引きを送る」は、取りこぼしが出たときに数がずれたままになるのでやめた

## 確かめ中に見つけた不具合

- **登録すると、選んだ船が上書きされる**：準備画面は、登録・ログインのあとに保存してある船を読み直す。保存が無いと、「アカウントから決まる船」を選び直していたため、**先に自分で選んだ船が消えた**。最初の通し確認は「ベル」を選んで通ったが、アカウントから決まる船がたまたま「ベル」だった（3 分の 1）。コードを読み直して気づき、「自分で選んだか」を覚えて上書きしないようにした。**直したあと、3 種類の船を選んで登録 → 出発し、保存された船が選んだものと一致することを、WebGPU・WebGL2 の両方で確かめた**。1 回通ったことだけでは、偶然を見分けられない
- **登録が `INVALID_ORIGIN` で断られた**：別のポート（5174）で開発サーバーを動かして確かめたため。`BETTER_AUTH_URL` は 5173 番。人が動かしている 5173 番を止めない決まりなので、手元（localhost）のときだけ、別のポートも信頼するようにした（本番には効かない）

## 確かめ方の注意

- 「WebGL2 の確認」のつもりで起動しても、Chrome for Testing は引数なしで `navigator.gpu` が使えた。**本当に WebGL2 だけにするには、ページが読まれる前に `navigator.gpu` を消す**（`addInitScript`）。そうして初めて、`THREE.WebGPURenderer: WebGPU is not available, running under WebGL2 backend.` の警告が出た
- WebGL の canvas は、描き終わったあとに別の canvas へ `drawImage` で読み出すと空になる。船が描けているかは、読み出さず、画面のスクリーンショットで見た
- `curl` を zsh で使うとき、`-H` を変数に入れて展開すると、単語に分かれない。Node のスクリプトで確かめた

## 残っていること

- Google ログインとパスキー、パスワードを忘れたときの戻し方、世界からタイトル画面・準備画面へ戻る入口：[`requirements.md`](../../product/requirements.md) の「決まっていないこと」
- 本番に出す前：登録・ログインの試行の制限、`/api/presence` の制限（[`server.md`](../../tech/server.md)）
- 画面の細部（文言・星空と地球の縁の見た目）は仮
