# ユーザー名とパスワードを忘れたときの回復コード

最初の登録（ユーザー名＋パスワード）は、忘れると戻せなかった。オーナーから「忘れたときのリカバリーを考えたい」とあり、選択肢を比べて回復コードを作った。仕様は [`../../product/top-screen.md`](../../product/top-screen.md)、仕組みは [`../../tech/server.md`](../../tech/server.md)。

## 比べた案と判断（2026-11-06）

メールを集めていないので、「届け先」が無いのが前提だった。

| 案 | 判断 | 理由 |
|---|---|---|
| 回復コード | **作った** | パスワードもユーザー名も戻せる。外のサービスも個人情報も要らない。保存し忘れると戻せないのが弱点 |
| 最後のユーザー名を端末に覚える | **作った** | ごく小さい作業で、名前だけを忘れた場合の多くが足りる |
| パスキー | **次に作る** | 入力なしで入れる。新しいパッケージが要る。端末をすべて失うと戻せないので、回復コードと併用する |
| メール（任意登録） | 見送り | 送るサービスと個人情報の扱いを先に決める必要がある |
| Google 連携 | 見送り | メールを保存すると、取り扱いの責任が運営側に生じる（オーナーの質問で整理した）。Google Cloud の設定とブランド確認も要る。公開の形が決まってから考える |
| 秘密の質問 | 入れない | 答えを推測されやすい |

オーナーは「ユーザー名＋パスワード＋（回復コード＋パスキー）」の段階的な足し方で OK とした。パスワードをやめるかは、パスキーが動いてから決める。

話の途中で、私が「ユーザー名＋パスワードなら個人情報が増えない」と言ったのは言い過ぎだったと分かった。session テーブルに User-Agent を保存している（IP の欄もある）。扱いは [`requirements.md`](../../product/requirements.md) の「決まっていないこと」に置いた。

## つくり方の判断

- **1 人 1 つを作り直せる形（仮）**：8 個を一度に出す予備コード方式より、画面が単純。使うと新しいコードが出るので、続けて困らない
- **遅いハッシュを使わない**：コードは 100 ビットあり、総当たりできない。パスワードと違って遅いハッシュは要らず、SHA-256 で引ける
- **ユーザー名を教えるだけなら、コードを使い切らない**：名前を思い出したいだけの人に、新しいコードを保存させる手間をかけないため
- **作り直しにパスワードを求める**：ログインしたままの端末を他人に触られても、コードを作り直されないように
- **決め直しは D1 の batch で直接行う**：Better Auth の関数を順に呼ぶと、途中で失敗したときに「パスワードは変わったがコードは古いまま」などになる。パスワードの更新・セッションの全削除・コードの置き換えを、まとめて成功か失敗にした。どの文も古いコードが有効なことを条件にしたので、同時に送られても 1 回しか効かない（実際のサーバーで、同時に 2 回送って片方だけ成功した）
- **閉じるには「保存しました」が要る**：閉じると二度と見られないため。ブラウザの `<dialog>` を使い、後ろの画面を触れないようにした（出発で画面を離れて、コードを失わないように）

## 確かめ中に直したこと

- **「このユーザー名でログインする」で、別の名前が入る**：モードを切り替える処理が「最後に使った名前」を入れるので、順序によっては見つけた名前が上書きされた。コードを読んで気づき、端末に別の名前を入れた状態で確かめた
- **登録の直後に、コードの画面が作り直される**：登録で画面の分岐が変わると、React がコードの画面を別物として作り直し、チェックが消えていた。分岐の外の同じ位置に置いた
- **読み直しの失敗で、コードの画面が消える**：通信に失敗すると、アカウントの部品ごと消える作りだった。一度読めたあとは消さないようにした（ただし、この失敗そのものは起こして確かめていない）

## 残っていること

- パスキー、Google ログイン、ログインの記録の扱い：[`requirements.md`](../../product/requirements.md) の「決まっていないこと」
