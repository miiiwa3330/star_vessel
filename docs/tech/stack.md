# 技術スタック

Web アプリとして作り、PC とスマホの両方に対応する（[`../product/requirements.md`](../product/requirements.md) の N2〜N4）。Web で処理としてどこまでできるかは [`feasibility.md`](feasibility.md)。

選定は2回に分ける。

1. **ブラウザ側（いま）**：描画・天体の計算・移動。最初に作る「世界の創造」に必要な分
2. **サーバー側・公開先（他のプレイヤーの機能を作る前）**：同時接続の規模とアカウントが決まってから選ぶ。公開先はサーバーと同じ場所にまとめたいので、このときに一緒に決める
   - 2026-11-05：ワープホールを全員で共有する（要件 F9）ためにもサーバーが要る。ワープホールの共有は、位置を毎秒送り合う通信と違い、保存と読み出しだけで足りる

## 決まったこと

- 2026-11-04：Web アプリとして作る。ネイティブアプリ化は必要になったら考える
- 2026-11-04：ブラウザ側は推奨どおりに決定（下の「ブラウザ側の選定」）
  - 描画：three.js（`three/webgpu`。WebGPU が使えない端末では WebGL2 に自動で切り替わる）
  - 世界の計算と描画は three.js を直接使い、操縦席の表示・メニューだけを React で作る
  - 天体の計算：astronomy-engine。自分たちの関数で包んで使う
  - 恒星のデータ：HYG v4.4。使う列だけを数値の並びに変換して配る
  - 開発の土台：Vite ＋ TypeScript ＋ Vitest
- 2026-11-05：**サーバー側は Cloudflare にまとめる**（下の「サーバー側の選定」）。Workers（入口・ブラウザ側の配信）、D1（ワープホール・アカウントの保存）、Durable Objects（宇宙の区画ごとの位置のやりとり）、アカウントは Better Auth（登録なしで始めて後から登録）。言語は TypeScript
- 2026-11-05：**satellite.js（MIT）を足した**。人工衛星の軌道要素（TLE）から位置を出す SGP4 の計算に使う（要件 F29）。SGP4 は自分で書くと誤りやすく、広く使われているライブラリを使う方が確か。`src/world/satellites.ts` の中だけで使う。版 7 は WebAssembly 版を Worker の中で読み込むので、Vite の Worker の出力を ES モジュールにした（`vite.config.ts`）
- 2026-11-04：ブラウザ側の言語は TypeScript。測って遅い所（天体の自動生成など）だけ、後から Rust（WebAssembly）か GPU の計算に移す。サーバー側の言語は別に選ぶ（下の「6. 言語」）

## ブラウザ側の選定（2026-11-04 決定）

比べた候補と理由。**太字**が採用したもの。バージョンは 2026-11-04 に npm で確かめた最新版。

### 1. 描画（3D）

| 候補 | 特徴 | 合うか |
|------|------|--------|
| **three.js**（0.187・MIT） | 3D 描画の部品だけを持つ軽いライブラリ。`three/webgpu` の描画は WebGPU を使い、使えない端末では自動で WebGL2 に切り替わる。情報・作例がいちばん多い | **推奨**。座標の付け替え・星の描き方・距離での描き分けを自分で組む必要があり、決まった仕組みを持たない方がぶつからない。必要な分だけ読み込めるので、スマホでも軽く保てる |
| Babylon.js（9.33・Apache-2.0） | 物理・UI・調査用の画面まで揃ったエンジン。WebGPU 対応 | 機能が揃うぶん重い。物理などは今の要件で使わない |
| PlayCanvas（2.23・MIT） | エディタ付きのエンジン | エディタ中心の作り方になる。コードで世界を生成する本件では利点が薄い |
| Unity・Godot の Web 書き出し | ゲームエンジンで作ってブラウザ向けに書き出す | 最初のダウンロードが大きく、スマホのブラウザで重い。**不採用を推奨** |

### 2. 3D と画面の部品（操縦席の表示・メニュー）のつなぎ方

| 候補 | 特徴 | 合うか |
|------|------|--------|
| **世界は three.js を直接、画面の部品は React** | 世界の計算と描画は React の外で毎フレーム回し、操縦席の表示やメニューだけ React で作る | **推奨**。世界は毎フレーム大量の位置を更新し、座標も付け替える。直接書く方が速く見通しがよい。世界の計算を画面から切り離した関数にでき、テストしやすい（AGENTS.md の「実装の方針」） |
| React Three Fiber（9.8・MIT）で全部 React | 3D も React の部品として書く。作例・部品集（drei）が多い | 小さな場面には便利だが、世界全体を React の仕組みに通すと、毎フレームの更新を React の外へ逃がす工夫が増える |

### 3. 天体の位置・自転の計算

中身・できること・できないことは [`astronomy-data.md`](astronomy-data.md)。

| 候補 | 特徴 | 合うか |
|------|------|--------|
| **astronomy-engine**（2.1.19・MIT） | 太陽・月・惑星・冥王星の位置、木星の4大衛星、惑星の自転軸を時刻から計算する。他のライブラリに頼らない。精度が高い | **推奨**。最後の更新は 2023 年だが、計算式は古くならない。差し替えられるよう、自分たちの関数で包んで使う |
| astronomia（4.2.0・MIT） | 天文計算の定番の教科書（Meeus）の式を集めたもの | 使える。ただし使い方が低レベルで、組み立てる手間が多い |
| 自分で書く（JPL の近似の軌道要素） | 惑星の軌道を公開されている近似式で計算する | 見た目には十分な精度。上の2つが扱わない衛星（土星の衛星など）はこの方法で足す |

### 4. 恒星のデータ

中身・注意点・ライセンスは [`astronomy-data.md`](astronomy-data.md)。

| 候補 | 特徴 | 合うか |
|------|------|--------|
| **HYG データベース** | 明るい星約12万個の位置・明るさ・色をまとめたもの。ライセンスは CC BY-SA 4.0（使う前に原文で確かめる） | **推奨**。そのまま星空にでき、ブラウザで扱える量 |
| Gaia DR3（ESA）の一部 | 約18億個から必要な範囲を切り出す | 量が多い。HYG で足りなくなったら足す |

### 5. 開発の土台

| 候補 | 合うか |
|------|--------|
| **Vite（8.3）＋ TypeScript（7.0）** | **推奨**。three.js と組み合わせる標準的な構成で、開発中の表示の更新が速い |
| **Vitest（5.1）** | **推奨**。Vite と設定を共有できる。天体の位置・座標の計算をテストする |

### 6. 言語（Rust・Go を使うか）

ブラウザで動かせるのは JavaScript（TypeScript）と WebAssembly（Wasm）。Rust は Wasm に変換しやすい。Go も変換できるが、Go 自体の実行の仕組みを一緒に持ち込むためファイルが大きくなり、ブラウザ向きではない。

**処理の時間がどこにかかるか**で考える。

| 処理 | どこで動くか | 言語で速さが変わるか |
|------|--------------|----------------------|
| 描画（星・惑星・宇宙船を画面に描く） | GPU。命令はシェーダーの言語（WGSL・GLSL）で書く | **変わらない**。どの言語から呼んでも GPU の仕事は同じ。速さは描く数・描く回数・シェーダーの重さで決まる |
| 惑星・衛星の位置の計算 | CPU | ほぼ変わらない。数百個でも1フレームの中のごく一部の時間で終わる |
| 天体の自動生成（移動するたびに、周りの星系を作る） | CPU か GPU | **ここだけは変わりうる**。数値計算の繰り返しは Wasm のほうが速くなることがある。ただし大量に作るなら、GPU で計算させる（WebGPU の計算機能）方がさらに速い |
| 画面のカクつき | CPU | 言語より書き方。毎フレーム新しい値を作って捨てると、JavaScript の掃除（GC）で止まる。入れ物を使い回せば防げる |

- **推奨：TypeScript で始め、測って遅い所だけを Rust（Wasm）か GPU の計算に移す。** 最初から Rust にすると、ビルドの準備・JavaScript との受け渡し・作り直しの手間が増えるが、遅くなりやすい描画には効かない
- 移しやすくするため、自動生成は「入力（場所・種）→ 出力（天体の一覧）」の決まった形の関数にし、別スレッド（Web Worker）で動かす
- Rust だけで全部書く案（Bevy などのエンジンを Wasm で動かす）もある。ただしファイルが大きくなり、画面の部品を作る手段が少なく、スマホのブラウザでの実績も少ない
- **サーバー側は話が別。** 全世界のプレイヤーの位置を受け取って配る処理は、人数が増えるほど重くなり、言語の速さが効く。Go・Rust はサーバー側の選定で有力な候補にする

## サーバー側の選定（2026-11-05 決定）

**太字**が採用したもの。

### サーバーに求めること

| 何のために | 求めること | 要件 |
|-----------|-----------|------|
| ワープホールの共有 | 保存と読み出し。1人3個までの制限、通し番号を重ならずに振る、置いた本人だけが消せる | F9・F12・F13 |
| 他のプレイヤーの宇宙船 | 数百人が1秒に数回ずつ位置を送り、近くの人にだけ配る | F2・N5 |
| あいさつ・スタンプ | 近くの人に短いメッセージを配る | F6 |
| アカウント | 登録なしで始め、後から Google などで登録して同じ記録を引き継ぐ | F14 |
| 公開 | ブラウザ側（静的なファイル）を世界中に配る | N2 |

ワープホールの共有は保存と読み出しだけで足りるが、宇宙船の位置は**途切れない双方向の通信（WebSocket）**が要る。候補は、この2つを両方こなせるかで比べた。

### 候補

| 候補 | 中身 | 合うか |
|------|------|--------|
| **Cloudflare（Workers ＋ Durable Objects ＋ D1）＋ Better Auth** | Workers が入口とブラウザ側の配信、D1（SQLite）がワープホールとアカウントの保存、Durable Objects が宇宙の区画ごとの位置のやりとり（WebSocket）。登録なしで始めて後から登録する仕組みは Better Auth（1.7・MIT）の anonymous プラグイン | **推奨**。1つのサービスに全部まとまる。Durable Objects は「区画ごとに1つの部屋」を作る仕組みで、近くの人にだけ位置を配る作りにそのまま合う。言語はブラウザ側と同じ TypeScript で、計算のコード（`src/world/`）を共有できる |
| Supabase（Auth ＋ Postgres ＋ Realtime） | 登録なしで始めて後から登録する仕組みが標準で付いている。ワープホールの保存は Postgres の決まり（行ごとの権限）で作れる | アカウントとワープホールには最も手早い。ただし Realtime は1秒あたりのメッセージ数に上限があり（無料 100・Pro 500・上限を外した Pro 2,500）、数百人が1秒に数回位置を送ると届いてしまう |
| Supabase（アカウント・ワープホール）＋ Cloudflare Durable Objects（位置） | 得意なところを分ける | 動くが、サービスが2つになり、ログインの情報を両方で確かめる手間が増える |
| Go か Rust の自前のサーバー（Fly.io など） | 位置のやりとりを自分で書く | 速さは最も出せるが、サーバーの運用・アカウントの仕組みを自分で持つ。数百人ではそこまでの速さは要らない |

### 費用の目安（Cloudflare・2026-11-05 に公式の料金ページで確認）

- Durable Objects は無料プランでも使える（SQLite 型のみ）。無料はリクエスト 10 万／日まで
- 有料（月 $5）はリクエスト 100 万／月を含み、超えた分は 100 万あたり $0.15。**受け取る WebSocket のメッセージは 20 件で 1 リクエスト**、送り出すメッセージは無料
- 例：常に 300 人が 1 秒に 2 回位置を送ると、受け取るメッセージは 1 日約 5,200 万件 → 約 260 万リクエスト／日。月に約 7,800 万リクエストで、約 $12 ＋ 月額 $5 程度。待機中は休止（hibernation）させれば時間の料金はかからない
- ワープホールの共有だけなら、無料プランに収まる

### 言語（Go・Rust は要るか）

2026-11-04 に「サーバー側は Go・Rust が有力」と書いた。数百人の規模なら、1つの区画（Durable Object）が受け持つ人数は少なく、TypeScript で足りる。人数が増えたら区画を細かく分けて負荷を散らす。Durable Objects は Rust（WebAssembly）でも書けるので、遅い部分が出たらそこだけ移せる。

## 選ぶ前に考えておくこと

要件から、どの技術を選んでも向き合う課題。

- **リアルタイムの同期**：全世界のプレイヤーの位置を送り合う仕組みがいる。全員に全員の位置を送ると人数の2乗で重くなるので、近くの船だけ細かく送る仕組みが必要（サーバー側の選定で扱う）
- **とても広い座標**：銀河の規模の座標を、そのまま3D描画の数（32bit の小数）で持つと、遠くで位置がガタつく。位置は 64bit で持ち、描くときに自分の船を原点に置き直す
- **天体の位置の計算**：惑星の公転・自転を現実の時刻から計算する。全員が同じ時刻を使えば同じ位置になるので、天体の位置は通信で送らなくてよい。端末の時計のずれをどう補正するかは考える
- **天体の自動生成**：同じ場所なら誰が見ても同じ天体になるよう、決まった種（シード）から生成する
- **距離による描き分け**：近くは細かく、遠くは点や光でまとめて描いて軽く保つ
